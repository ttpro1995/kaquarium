# Security Requirements — u6-commerce

> Upstream: `functional-design/functional-spec.md` (W26–W35), `rules.md` (BR16–BR19), `requirements.md` (NFR2, NFR3, NFR4, NFR5), `contract-summary.md` (C2 determinism + purchase-path exception, C4 event catalogue, C6 import pipeline). Answers from `nfr-requirements-questions.md` (Q1–Q4 all A).
> Threat posture: same as U2–U5 (browser-local, no network/auth/PII/secrets). Commerce-specific surfaces: money scalar integrity (non-negative, atomic deduct-or-reject), order fulfilment validation (no free money), notification queue bound (cap 100, criticals may overflow per BR19.3).

| ID | Requirement | Source | Verification |
|---|---|---|---|
| NFR3.1 | Market determinism: trend re-rolls, order generation draws (species/customer/deadline), and reward math draw only through `ctx.rng` while iterating species in ascending speciesId order (canonical catalogue order, fixed at boot — replay never depends on file load mechanics) then the board in board-array order; no per-tick sort. Replay reproduces every price, trend, order, and level-up. | NFR3 | Golden replay test: scripted sales → saturation → order cycle matches stored state. |
| NFR4.1 | Commerce-state migration, single owner: the v1 → v2 migration fills `MarketState.lastTrendDay` (= max(1, game day at migration); game day counts from 1 per `START_DAY`), converts built `Order` fields instead of discarding them (`deadline` → `deadlineDay`, falling back to game day + 3 when below the current day; `minQuality` → `minHealth`; `minSizeCm` from the catalogue market size), defaults only what has no built equivalent (`customer` hobbyist, `multiplier` 1.2), preserves quantity/species/reward, and fills `Notification.subjectId = ''` when absent (register rows amended into the U2 breaking-change register; no load-defaulting path). `PlayerProgression` needs no migration (`xpToNext` stays derived). | NFR4 | v1 fixture → migrated commerce state equals a fresh v2 save; open-order fixtures keep their economics and their size/health gates. |
| NFR4.2 | U6 never reads raw save payloads; all commerce state enters through the C6 import pipeline plus the U2-owned NFR4.3 bounded import barrier, with these explicit U6 inputs to that barrier (owner: U1 kernel; enforced post-migration, pre-runtime, INVALID_SHAPE on violation): per-market — demand 0–2, trend −1/0/1, lastTrendDay integer ≥ 1 (game day counts from 1); per-order — quantity integer ≥ 1, multiplier > 0, minHealth 0–100, minSizeCm ≥ 0, deadlineDay integer; progression level 1–3, xp integer ≥ 0; notifications ≤ 100 (already capped). Money handlers stay atomic per the C2 purchase-path exception. | NFR4 | Import suite rejects malformed commerce state without touching the current save, including hand-stamped fixtures (negative demand, L9 progression, 101st notification). |
| NFR5.1 | Commerce logic is test-first (TDD) with the 80% line-coverage floor and CI gate; price-formula, saturation, fulfil-premium, level-threshold, and queue-cap paths carry boundary tests. | NFR5 | Coverage report + CI block on failure. |
